## High

### 1. `git diff` reduction is not bounded by the 10 000-character retained-output budget

`MAX_RETAINED_OUTPUT_CHARS = 10_000` (`src/tool-output.ts:40`) gates *which* outputs get reduced, but `formatDiffSummary` never applies it to its own output. It emits one line per changed file and up to 12 hunk headers **per file** — both unbounded in file count — and caps only the excerpt:

```ts
// src/tool-output.ts:300-302
const fileLines = [...files].map(([path, stats]) => `- ${path} (+${stats.added}/-${stats.deleted})`);
const hunkLines = [...files].flatMap(([path, stats]) => stats.hunks.slice(0, 12).map((hunk) => `- ${path}: ${hunk}`));
const changeExcerpt = fitExcerpt(selectExcerpt(changedLines, 80), 7_000);
```

The only size guard is `if (compactedText.length >= originalText.length)` (`src/tool-output.ts:384`), which a large diff passes while still exceeding the budget by orders of magnitude.

Measured — `reduceToolOutput({ toolName: "bash", input: { command: "git diff main" }, … })`:

| files | original chars | retained chars | ~retained tokens | × 10 000-char budget |
|---:|---:|---:|---:|---:|
| 50 | 36 710 | 5 795 | 1 449 | 0.6× |
| 500 | 369 060 | 31 814 | 7 954 | 3.2× |
| 2 000 | 1 481 560 | 120 832 | 30 208 | 12.1× |
| 8 000 | 5 939 560 | **480 833** | **120 209** | **48.1×** |

A separate run on an 8 MB / 4 000-file diff retained 194 516 characters.

**Failure mode.** A repo-wide `git diff` on a large branch produces a "reduction" that by itself consumes ~120 k tokens — five times the aggressive-profile compaction threshold (`compactThresholdTokens: 24_000`, `src/config.ts:31`). Telemetry records it as a *successful* reduction (positive `removedTokens`), so the soft-warning and compaction loop then react to size the reducer just injected. Growth is linear in file count; nothing bounds it except the diff happening to be small.

**Suggested fix.** Route the file and hunk sections through the same budget as every other category, and make the overflow explicit rather than silent:

```ts
function formatDiffSummary(lines: string[]): string {
  // ...existing parse loop...
  const fileLines = [...files].map(([path, stats]) => `- ${path} (+${stats.added}/-${stats.deleted})`);
  const hunkLines = [...files].flatMap(([path, stats]) =>
    stats.hunks.slice(0, 12).map((hunk) => `- ${path}: ${hunk}`),
  );
  const cappedFiles = fitExcerpt(fileLines, 3_500);
  const cappedHunks = fitExcerpt(hunkLines, 2_000);
  const changeExcerpt = fitExcerpt(selectExcerpt(changedLines, 80), 3_500);
  const omitted = files.size - countIncludedFiles(cappedFiles, fileLines);
  const sections = [
    `Files changed: ${files.size}${omitted > 0 ? ` (details truncated for ${omitted} files)` : ""}`,
    cappedFiles.length > 0 ? cappedFiles : undefined,
    // ...
  ];
}
```

Two supporting changes make the guard trustworthy rather than advisory:

1. Add a final assertion in `reduceToolOutput` that no category may retain more than `MAX_RETAINED_OUTPUT_CHARS` (plus the fixed header/excerpt allowance), so a future category cannot reintroduce this class of defect.
2. When a diff is truncated, say so in the header and name the count of omitted files — the existing `NON_EXHAUSTIVE_NOTICE` is a good fit, but only if the summary admits what it dropped.

### 2. Reduced headers assert an exit status that was never observed

`tool_result` exposes only `isError`. The header nonetheless prints a concrete number:

```ts
// src/tool-output.ts:199
const status = isError ? parseExitStatus(originalText) : "0";

// src/tool-output.ts:210-212
function parseExitStatus(text: string): string {
  const match = text.match(/(?:exit(?:ed)?|status|code)\s*(?:code\s*)?[:=]?\s*(-?\d+)/i);
  return match?.[1] ?? "non-zero";
}
```

Measured both branches:

- `isError: false` → **always** `Exit status: 0`, whatever the process actually returned.
- `isError: true`, `npm test`, body containing `http status: 404 not found` → header printed **`Exit status: 404`** while the real shell exit code was 1. The regex is unanchored and case-insensitive, so it harvests the first `exit`/`status`/`code`-adjacent integer anywhere in the output (`statusCode 500`, `error code 8`, `status404`, …).

**Failure mode.** The header is precisely the text that survives compaction and lands in summaries, so the model inherits a fabricated exit code and reasons about the wrong failure: a 404 status line becomes the process exit code, or a non-zero run is asserted as `0`. Nothing marks the value as inferred rather than observed.

**Suggested fix.** Report only what is known, and keep the harvested value as separately-labelled diagnostics instead of a verdict:

```ts
const status = isError
  ? "non-zero (exact code not reported by the tool)"
  : "reported successful";
```

If the numeric hint is worth keeping, move it out of the status line so it cannot be read as the exit code:

```ts
const hint = isError ? parseExitStatus(originalText) : undefined;
// …
hint ? `Exit status: non-zero (a "${hint}" code-like value appears in the output; unverified)` : …
```

Rename `parseExitStatus` to something honest (`guessStatusCodeFromOutput`) so the inference is visible at the call site, and add a test asserting that a failed command whose stdout contains `status: 404` never renders `Exit status: 404`.

### 3. Recovery-file prune deletes files the live conversation still cites

`appendFullOutputNotice` writes `Full output saved to: <path>` into the retained tool result (`src/tool-output.ts:421-436`), while `prune()` evicts FIFO on **every** `save()`:

```ts
// src/tool-output.ts:486-499
while ((this.managedFiles.length > this.maxFiles || totalBytes > this.maxBytes) && this.managedFiles.length > 1) {
  const oldest = this.managedFiles.shift();
  if (oldest) {
    totalBytes -= oldest.size;
    await rm(oldest.path, { force: true }).catch(() => undefined);
  }
}
```

Measured with production defaults (`maxFiles: 50`, 50 MB): after the 51st save, file #1 is `ENOENT` while the retained context still names it. With `{ maxFiles: 3 }`, saving five files left `output-1-bash.txt` and `output-2-bash.txt` `GONE (ENOENT)`; files 3–5 survived.

Aggravating factor: `session_shutdown` performs `void cleanupRecoveryStorage()` (`src/index.ts:648`), wiping the whole directory. Every `Full output saved to:` pointer inside a resumed or forked transcript is therefore dead, while `NON_EXHAUSTIVE_NOTICE` continues to tell the model the full output is retrievable.

**Failure mode.** The reduced excerpt is explicitly *not* authoritative — that is the whole reason the recovery copy exists. Once a file is evicted, the model's only recovery path returns ENOENT and it gets no signal that the pointer expired, so it either re-runs an expensive or non-idempotent command or proceeds from the lossy excerpt believing it is complete. Note this is the same dangling-reference class that the prior joint audit fixed for the embedded path (`plans/joint-project-audit-feedback.md`, recommendation 2 — `deactivate()` vs `dispose()`); the root path has no equivalent, and `prune()` adds an in-session trigger the embedded fix does not address.

**Suggested fix.** Make the pointer's lifetime observable and keep it alive as long as the conversation can still cite it:

1. **Never evict a file the live session can still reference.** Cheapest correct version: raise the eviction unit from "file" to "the tool result that referenced it" is impractical, so instead make prune LRU-on-actual-read plus generous — and, critically, when a file *is* evicted, rewrite nothing (impossible) but stop creating the illusion: keep `maxFiles` bounded by *bytes referenced by retained context*, which `session_before_compact`/`buildContextEntries` already lets the extension estimate.
2. **Stamp the notice with its expiry.** Emit `Full output saved to: <path> (retained for this session only; may be pruned after 50 later outputs)`, so a failed `read` is an expected outcome the model can handle rather than a contradiction.
3. **On prune, record it** via `debugLog` and the evidence tracker, so `/context-stats` can report "N recovery copies pruned" instead of silently losing them.
4. **Decouple shutdown cleanup from pointer lifetime**, mirroring the embedded fix: delete on real process exit, but leave a session-scoped directory (keyed by session id rather than `mkdtemp`) that a resumed session can either reuse or explicitly discard. A deterministic per-session path also makes a boot-time sweep of stale `pi-lcm-recovery-*` directories possible, which today has no TTL and no reaper after a crash.

### 4. The documented `0600`/`0700` guarantee does not hold on Windows, and CI never runs Windows

The repository's own suite fails on a Windows host today:

```text
FAIL  test/tool-output.test.ts > tool-output reduction > creates recovery copies with file permissions 0600 and directory 0700
AssertionError: expected 438 to be 384 // Object.is equality      (0o666 vs 0o600)
```

libuv/NTFS do not enforce POSIX mode bits, so `writeFile(..., { mode: 0o600 })` and `chmod(path, 0o700)` are effectively no-ops and the files inherit `%TEMP%` ACLs. `chmod(...).catch(() => undefined)` swallows even a genuine failure silently. `.github/workflows/ci.yml:16` is `os: [ubuntu-latest, macos-latest]`, so neither CI nor `prepublishOnly: npm run check` ever observes this — and on Windows `npm run check` cannot pass at all, which also blocks `npm publish` from that platform.

**Failure mode.** README advertises "bounded session recovery storage (`0700` dir / `0600` files)". Those files hold *full, untruncated* tool output — including whatever a `curl`, `ps`, `env`, or `.env`-`cat` command emitted — at a predictable `pi-lcm-recovery-*` path under the shared temp directory, with inherited rather than restrictive ACLs on the platform the extension does not test.

**Suggested fix.**

1. Make the Windows case honest rather than silently different. Either detect `process.platform === "win32"` and skip the mode-assertion path while documenting the limitation in README, or implement it properly by hardening the created directory with `icacls <dir> /inheritance:r /grant:r "<user>:(OI)(CI)F"` (drop inherited ACEs, grant only the current user, inherit into children). The cheaper option is a documented one — but the documentation must stop claiming `0600`/`0700` on a platform where those bits do not exist.
2. Fix the test so it asserts the *guarantee* rather than the platform's mode bits:
   ```ts
   if (process.platform !== "win32") {
     expect(mode).toBe(0o600);
   } else {
     // Windows: mode bits are not an access-control mechanism here.
   }
   ```
3. Add `windows-latest` to the CI matrix (`.github/workflows/ci.yml:16`). The suite is already portable enough to run; without this job, every future Windows regression — including this one — stays invisible until a user reports it.
4. Consider whether recovery copies should exist at all for commands whose output matched a secret-like pattern; today the reduction *improves* context hygiene in the transcript while quietly writing the unredacted original to disk.

## Medium

### 5. Command classification matches keywords inside quoted arguments

```ts
// src/tool-output.ts:44-48
const SUCCESSFUL_COMMAND_RE = /\b(?:build|test|check|lint|…|npm|pnpm|yarn|cargo|…)\b/i;  // no positional anchor
const SEARCH_COMMAND_RE = /(?:^|[;&|\s])(?:rg|ripgrep|grep|git\s+grep|find)\b/i;        // \s also matches inside quotes
```

Measured with probe 1:

| command | resulting category |
|---|---|
| `git commit -m 'find root cause of test failures'` | `build` |
| `echo cargo build failed` | `build` |
| `git log --oneline --grep=find` | `search` (and log-stream detection) |

Separately, `LOG_STREAM_COMMAND_RE` (`src/tool-output.ts:55`) includes the bare alternatives `log|trace|events|stream|concurrency` with an unanchored `\b`, so a plain `git log` is classified as a log/event stream and receives temporal-window excerpt selection.

**Failure mode.** The category is not cosmetic — it selects the reduction strategy and wording. A mislabelled `build` path can discard the lines that mattered while the header confidently reads `Reduced build output.`, which biases the model toward trusting a summary whose selection was chosen for the wrong reason.

**Suggested fix.**

1. Parse the command's leading executable and subcommand instead of regex-matching the whole string. Pi passes structured input (`input.command`); a single shell-word split that skips assignments and honours quotes, followed by matching `argv[0]`/`argv[1]` against the keyword sets, removes the entire class:
   ```ts
   const argv = splitShellWords(command);           // quote-aware
   const subject = `${argv[0] ?? ""} ${argv[1] ?? ""}`.trim().toLowerCase();  // "git diff", "npm test"
   ```
2. Anchor `SUCCESSFUL_COMMAND_RE` the way `SEARCH_COMMAND_RE` already is, at minimum `(?:^|[;&|]\s*)`, so a quoted argument cannot promote a command.
3. Drop the overly generic bare words (`log`, `trace`, `events`, `stream`, `concurrency`) from `LOG_STREAM_COMMAND_RE`'s command branch, or restrict that branch to known log subcommands (`docker logs`, `journalctl`, `kubectl logs`, `git log -p`). The line-shape heuristic `LOG_LINE_TIMESTAMP_RE` already handles real streams.

### 6. A hung fabric provider wedges the root session (no timeout)

`queryFabricObservation` awaits an untrusted provider with neither timeout nor `AbortSignal`:

```ts
// src/embedded/interop.ts:332-336
if (typeof (provider as FabricStateProviderV1).getSnapshot === "function") {
  rawSnapshot = await (provider as FabricStateProviderV1).getSnapshot!(request);
} else if (typeof provider === "function") {
  rawSnapshot = await (provider as FabricStateProviderFunction)(request);
}
```

Providers are registered by a *different* extension (`safe-agent-team.fabric-state.v1`) and perform broker IPC. Call sites include the `agent_settled` handler and `/context-stats`, and Pi awaits `agent_settled` handlers before resolving its idle promise (`_emitAgentSettled` in `dist/core/agent-session.js`).

**Failure mode.** A provider that never resolves keeps the root session from becoming idle, which also blocks LCM's deferred threshold compaction (`scheduleSettledCompaction` runs on `setImmediate` after the settled boundary) and the next prompt. The fail-closed `{ kind: "uncertain" }` path already exists and is exactly right — it is simply unreachable on a hang, because `catch` never runs.

**Suggested fix.** Bound the await and treat a timeout as the existing `uncertain` outcome:

```ts
const FABRIC_QUERY_TIMEOUT_MS = 2_000;

async function withTimeout<T>(promise: Promise<T>, ms: number, label: string): Promise<T> {
  let timer: NodeJS.Timeout | undefined;
  const timeout = new Promise<never>((_, reject) => {
    timer = setTimeout(() => reject(new Error(`${label} timed out after ${ms} ms`)), ms);
  });
  try {
    return await Promise.race([promise, timeout]);
  } finally {
    clearTimeout(timer);
  }
}

// at the call sites:
rawSnapshot = await withTimeout(callProvider(provider, request), FABRIC_QUERY_TIMEOUT_MS, "fabric state query");
```

Because the surrounding `catch` already converts a thrown error into `{ kind: "uncertain", reason: "Fabric query threw error: …" }`, this is a small behavioural change with no new state. Also thread `request.signal` (or Pi's `getSignal()`) into the provider call so a legitimate abort stops the peer's work instead of only being ignored.

## Low / latent

The mechanism in each is verified in source; the trigger is stated so the residual risk can be judged without re-reading the code.

### 7. The interop registry is replaced on a version mismatch, and `absent` means "safe"

```ts
// src/embedded/interop.ts:110-122
let registry = globalObj[PI_EXTENSION_INTEROP];
if (!registry || typeof registry !== "object" || registry.version !== 1 || !(registry.providers instanceof Map)) {
  registry = { version: 1, providers: new Map<string, unknown>() };
  globalObj[PI_EXTENSION_INTEROP] = registry;   // a peer's foreign registry is dropped
}
```

A peer that publishes a future `version: 2` registry (same `Symbol.for("pi.extension-interop.v1")` key) and LCM would each end up holding a private registry. LCM's provider lookup then returns `undefined` → `{ kind: "absent" }` → and:

```ts
// src/embedded/interop.ts:381-384
export function isSessionReplacementSafe(observation: FabricObservation): boolean {
  if (observation.kind === "absent") {
    return true;                       // no fabric extension installed ⇒ nothing to protect
  }
```

**Failure mode.** `/checkpoint-reset` — the destructive path — proceeds as though no children exist while children may be running under the peer's registry. This is the one place where protocol negotiation fails *open* rather than closed. Latent today: the only known peer speaks v1.

**Suggested fix.** Never clobber a well-formed foreign registry. If the global exists and is an object with a numeric `version` but not `1`, record "interop present, version unsupported" in module state, keep the peer's object untouched, and have `queryFabricObservation` return `{ kind: "uncertain", reason: "unsupported interop version" }` instead of falling through to `absent`. Reserve the permissive `absent` for the case that is actually permissive: no registry object at all. Optionally negotiate by having both parties advertise support and choosing the highest common version at some later point.

### 8. Fabric snapshot staleness and session identity are unbounded

`capturedAt` is validated only as a positive finite number and never compared with the present (`src/embedded/interop.ts:206-211`); `snapshot.rootSessionId` is sanitised (`src/embedded/interop.ts:284,304`) but never compared against the session LCM is running. A provider serving a cached, replayed, or foreign-session snapshot is accepted as `{ kind: "known" }` with `sessionReplacementSafe: true`.

**Suggested fix.** In `sanitizeFabricSnapshot`, reject snapshots whose `capturedAt` is in the future or older than a configurable ceiling (a few seconds is enough for a quiescence probe) — treat the rejection as `uncertain`, not `known`. Where the caller knows its own session id, compare `rootSessionId` and return `uncertain` on mismatch, which turns "another session's fabric state was believed" into the already-correct conservative branch.

### 9. `registerInteropProvider`'s conflict result is discarded at module scope

```ts
// src/index.ts:389
registerInteropProvider(LCM_EMBEDDED_CONTEXT_PROVIDER_NAME, embeddedContextProvider);
```

A duplicate name bound to a different object returns `false` (`src/embedded/interop.ts:124-136`) and the value is dropped, so LCM can start normally while the *previous* module instance's factory stays registered — with that module's own module-level `activeRecoveryStorage` singleton (`src/tool-output.ts:514`) behind it. Reachable through a reload/two-install setup, where `globalThis` outlives the module instance.

**Suggested fix.** Check the result and surface a conflict the way configuration warnings already are (`debugLog` plus `context.ui.notify(…, "warning")`), naming the provider and whether LCM or the incumbent won. If the incumbent is a stale instance, `unregisterInteropProvider` (`src/embedded/interop.ts:145`) exists to make the takeover explicit rather than accidental.

### 10. `managedFiles` desyncs after the recovery directory is removed externally

Measured: after the directory was deleted from outside the process, `getDirectory()` correctly detected the removal and created a new directory, but `managedFiles` kept the dead entries — `activeFilesCount` reported 2 with 1 file on disk — and `prune()`'s byte total kept counting the deleted bytes. The earlier path had already been handed to the model and was unreadable.

**Failure mode.** Over-counted bytes make prune evict *live* files earlier than the configured ceiling, compounding finding 3. The stale bookkeeping also makes `/context-stats` (if it ever reports storage occupancy) wrong.

**Suggested fix.** When `getDirectory()` discovers that its directory vanished, reset `managedFiles` (and `fileSeq` if desired) before creating the replacement — the old entries are provably unreachable. Additionally, `prune()` can drop entries whose `stat` fails so a partial external deletion does not permanently distort the accounting.

### 11. A relative `checkpointDirectory` resolves inside the repository

```ts
// src/checkpoint-reset.ts:230
return normalize(isAbsolute(expanded) ? expanded : resolve(cwd, expanded));
```

**Failure mode.** Checkpoint archives — conversation summaries, coordination state, repository state — land in the working tree, where they show up in `git status` and can be committed, including by an agent that is told to "commit everything". Project-level config is honoured whenever `isProjectTrusted()` is true, so a cloned repository can steer that path.

**Suggested fix.** Default to a directory under the Pi agent dir rather than `cwd`, and when a relative path is configured, resolve it against the agent dir (or `~`) instead of the repository, or require an absolute path and report a config error otherwise. At minimum, emit a one-time warning when the resolved directory is inside `cwd`, and add `checkpointDirectory`'s default to the repo's `.gitignore` guidance in README.

### 12. `/checkpoint-reset` cannot write checkpoints on volumes without hard links

```ts
// src/checkpoint-reset.ts:308-317
try {
  // rename() would replace a file if another reset chose this path first.
  // A hard link publishes the completed file atomically without clobbering it.
  await link(temporaryPath, path);
} catch (error) {
  if (errorCode(error) === "EEXIST") {
    throw new Error(`Checkpoint already exists: ${path}`);
  }
  throw error;   // EPERM / EXDEV / ENOSYS on ExFAT, many network and cloud-synced volumes
}
```

**Failure mode.** On such a volume the command always fails, with a raw link error rather than something actionable. It fails *safe* — nothing is written, and the `finally`-style cleanup removes the temp file — so this is a usability gap, not a corruption risk.

**Suggested fix.** Keep the no-clobber property and add a fallback: try `link()`, and on `EPERM`/`EOPNOTSUPP`/`ENOSYS`/`EXDEV` fall back to `open(path, "wx")` + write, which is atomic w.r.t. creation and equally immune to the clobber the comment guards against. Surface the fallback in debug output so a slow volume is diagnosable.

### 13. `/context-mode` discards user-tuned thresholds with no way back

```ts
// src/index.ts:1096-1100
config = {
  ...config,
  contextProfile: profile,
  ...CONTEXT_PROFILE_THRESHOLDS[profile],   // clobbers keys the user set explicitly
};
```

**Failure mode.** A user who tuned `compactThresholdTokens`/`softWarningTokens` in `local-context-manager.json` loses those values for the remainder of the session by switching profile, and has no in-session way to return to the configured numbers — only a restart. The message says "for this session" but does not say the config values are gone.

**Suggested fix.** Keep the loaded config immutable (it already is, conceptually) and hold profile overrides in a separate variable that `resolveThresholds` consults with the documented precedence `session override → config file → profile default`. Accept `/context-mode` with no argument plus a `reset`/`config` keyword to drop the override, and report which layer produced the effective thresholds in `/context-stats`.

## Checked and ruled out

Recorded so the next pass does not re-litigate them.

| Hypothesis | Result |
|---|---|
| Regex / quadratic blowup while reducing hostile tool output | **Not a defect.** 8 MB single-line JSON → 18 ms; 10 MB single line with 2 M spaces → 40 ms; 8 MB / 4 000-file diff → 141 ms. `HIGH_PRIORITY_RE` is not a hazard. |
| `CompactionGate` can latch in flight forever | **Not a defect.** `context.compact(options)` always invokes `onComplete` **or** `onError` (`dist/core/agent-session.js:2069-2080`), and `session_start` builds a fresh gate (`src/index.ts:590`). The `event.reason !== "manual"` filter in `session_compact_failed` (`src/index.ts:825-831`) is redundant, not a stall. |
| Concurrent `save()` races `mkdtemp` and orphans temp directories | **Not a defect.** 24 concurrent saves produced 24 distinct files in **1** directory, and `cleanup()` removed it completely. |
| `extendFileOperations` targets tool names Pi does not have | **Not a defect.** Pi's built-ins are `read`/`bash`/`edit`/`write` (plus `grep`/`find`/`ls`) and match. |
| Embedded reduction loses data when recovery storage fails | **Not a defect.** It deliberately preserves the original output, per the prior audit. |
| Prior joint-audit recommendations 1–2 (`isRootOnlyLag` / trusting `quiescent`, `deactivate` vs `dispose` recovery retention) | **Already implemented.** Recommendation 3 belongs to `pi-safe-agent-team`. |
| `session_compact` credits a Pi-internal threshold compaction as LCM's pending request (`src/index.ts:773-821`) | **Benign.** Context pressure is relieved either way and telemetry marks compaction once; the pending request is dropped, not double-counted. |
| `selected.clear()` in `selectExcerpt`; the config ordering-repair loop can spin | **Dead code / unreachable.** The loop's "neither changed" branch cannot be reached; no infinite loop. |
