## Round 3 verdict

PR #19 is a meaningful improvement. The central R2 concern is now addressed correctly: ordinary proactive compaction and Pi overflow recovery use Pi's native preparation; LCM's deeper `keepRecentTokens` slice is reserved for an explicit semantic request. That is much closer to the desired rule of **“intervene early, but do not make Pi's recovery path harder.”**

I would now characterize the project as **substantially hardened, but not quite at final sign-off**. I found no new P0/data-loss issue, but there is **one deterministic compaction-policy bug** that can create the opposite failure from R2, plus a few lifecycle/integration problems worth resolving.

### R2 closure

| R2 concern                                                              | R3 assessment                                                                                                                         |
| ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Deeper LCM compaction could worsen local-model prefill                  | **Fixed for routine threshold and overflow paths.** Deep slicing is now semantic-only.                                                |
| Gate could permanently retire after a high post-compaction result       | **Conceptually fixed**, but the new rearm logic has an inverse edge case described below.                                             |
| Recovery files deleted on fork/resume `session_shutdown`                | **Fixed for same-process session transitions**, but recovery storage is still process-global rather than genuinely session-addressed. |
| Hung fabric work not cancelled                                          | **LCM now propagates and aborts a signal**, but the current `pi-safe-agent-team` provider doesn't consume that signal end-to-end.     |
| Missing `rootSessionId` accepted for destructive reset                  | **Fixed.**                                                                                                                            |
| Single recovery item can violate `maxBytes`                             | **Fixed.** Oversized individual outputs now refuse reduction recovery and therefore preserve the original output.                     |
| Failed checkpoint fallback can leave a partial file after a write error | **Fixed for ordinary write failures.**                                                                                                |
| Local-model failure injection tests                                     | **Good addition.** The six scenarios directly target the R2 concerns.                                                                 |

The test suite is materially stronger. One caveat: in the CI run I inspected, 124 tests passed but three of the four real-Pi smoke cases were skipped because the companion extensions were unavailable. The smoke suite itself intentionally uses `runIf` for those cases.  So cross-extension behavior is not yet continuously exercised by normal CI.

## R3-1 — P1: successful compaction can now cause a periodic compaction loop

This is the most important R3 finding.

The new gate stores `postCompactionTokens`, which was the right fix. But `observe()` rearms whenever either:

* context has grown sufficiently from the post-compaction baseline, **or**
* current context is simply `>= compactThresholdTokens`.

The second condition is not actually a **threshold re-entry**. It is only a threshold level check.

Consider balanced mode:

```text
threshold = 32k
rearm = 24k

turn 1:
  compact at 34k
  compact succeeds but lands at 33k
  postCompactionTokens = 33k
  gate disarmed

turn 2 start:
  tokens still 33k
  tokens >= 32k -> gate ARMED
  cooldown prevents request this turn

turn 3:
  tokens still 33k
  cooldown elapsed -> compact again

compaction again lands at ~33k
repeat every two turns
```

There is **zero post-compaction growth**, yet the gate rearms. The current test covers `29k → 32k`, which is a legitimate threshold crossing, but does not test `33k → 33k`.

This case is quite plausible with a large irreducible recent turn, image-heavy context, long retained summary, or large system/context material. And on a local model, repeated summarization prefills every two turns are precisely something LCM should prevent.

The threshold condition should instead be something like:

```ts
const crossedThreshold =
  this.postCompactionTokens < compactThresholdTokens &&
  tokens >= compactThresholdTokens;
```

If the previous compaction **already landed above the threshold**, require meaningful growth from that baseline before rearming.

I would add this exact regression:

```text
complete(33_000)
observe(33_000, 32_000) -> disarmed
observe(33_500, 32_000) -> disarmed
observe(35_500, 32_000) -> armed
```

This is the one runtime fix I would make before another release.

## R3-2 — P1/P2: recovery is durable across shutdown now, but it is not really session-scoped

The R2 fix removed cleanup from `session_shutdown`, which correctly prevents a fork/resume from immediately invalidating recovery pointers.

But there is still exactly one module-global:

```ts
let activeRecoveryStorage = new SessionRecoveryStorage();
```

and `session_start` neither rekeys nor replaces it.

That creates three second-order problems.

**First, sessions share one LRU quota.** Session A can have 30 live referenced outputs; switch to unrelated Session B; B creates 30 more. B can evict A's outputs because all 60 belong to one 50-file process-global LRU. Resume A and its transcript now contains expired pointers.

That is better than before because a same-process manager remembers pruned paths, but it still means one unrelated session can destroy another session's recovery capability.

**Second, recovery metadata does not survive process restart.** The actual temp files may survive, but a fresh process has an empty `managedFiles` array and empty `prunedPaths`. It never adopts the old directory. Thus a resumed transcript may still successfully read the literal old path while it exists, but LCM no longer knows how to manage it, refresh its LRU status, or explain its eventual disappearance.

The R2 regression test only exercises `session_shutdown` and resume **within one process**, using the same `SessionRecoveryStorage` instance.

**Third, the three-day sweeper can delete another still-live process's recovery directory.** It decides staleness from directory `mtime`. Merely rereading an old recovery output does not touch that directory on disk. If Pi A has been alive for >3 days without creating another recovery file, a newly started Pi B can classify A's directory as stale and recursively delete it.

The robust model would be per-session recovery directories plus a small manifest/lease:

```text
pi-lcm-recovery/<session-hash>/
  manifest.json
  heartbeat
  output-...
```

A resumed session can reattach to its manifest; a new unrelated session gets a separate quota; stale cleanup uses a lease/heartbeat rather than only directory `mtime`. Forks can simply retain references to the parent's immutable recovery paths.

This also makes the model-facing wording honest. Today it says the copy is “kept for this session only,” while the actual object is process-global and survives session replacement.

## R3-3 — P1 operational: the hardened code is still called `0.4.3`, but `v0.4.3` is older code

This one is easy to miss and can undo the entire audit effort for users.

Current `main` contains the merged PR #19 hardening.  But `package.json` still says:

```json
"version": "0.4.3"
```

Meanwhile the existing `v0.4.3` tag points to commit `5ef08da...`, i.e. an older state before these audit fixes.

And the README explicitly tells users they can pin:

```text
pi install git:github.com/SaehwanPark/pi-local-context-manager#v0.4.3
```

So:

```text
recommended unpinned GitHub installation -> current hardened main
README's pinned "stable" example       -> pre-audit implementation
package built from current main         -> still identifies itself as 0.4.3
```

The changelog also ends at the old 0.4.3 hardening work and does not describe PR #18/#19.

I would bump this to at least **0.4.4**, arguably **0.5.0** given the behavioral changes, update the changelog, and tag the audited state. Until then, it is surprisingly easy for someone trying to be conservative by pinning a version to receive the less-safe version.

## R3-4 — P2: degraded `safe-agent-team` can still add repeated 2-second stalls and background requests

LCM now correctly aborts its local `AbortSignal` after the two-second fabric timeout.

But the actual current companion contract in `pi-safe-agent-team` defines:

```ts
interface FabricSnapshotRequest {
  cwd: string;
  sessionId?: string;
}
```

No signal is part of its contract.

Its snapshot implementation eventually calls `status()`, which performs a broker request; the broker client's normal request timeout is **60 seconds** and has no abort-signal parameter.

Therefore:

```text
LCM waits 2 sec
LCM aborts signal
LCM returns "uncertain"

but safe-agent-team's broker request can remain alive for ~60 sec
```

Repeated queries can accumulate those outstanding requests during a degraded broker episode.

There is also an LCM-side amplification: `agent_settled` performs `queryFabricObservation()` **unconditionally**, before determining whether any semantic/reset operation actually requires fabric state. Ordinary threshold compaction doesn't need fabric coordination at all.

So a broken optional companion can add a two-second delay to ordinary agent-settled processing and delay context protection that should be independent of it.

I would do both sides:

* In LCM, don't query fabric unless `semanticRequested || checkpointResetRequested` (plus explicit diagnostics/reset commands that genuinely need it). Threshold compaction should remain completely independent.
* In `pi-safe-agent-team`, accept `signal?: AbortSignal` through `FabricSnapshotRequest`, `getFabricStateSnapshot()`, `status()`, and `BrokerClient.request()`, with cancellation removing the request from `pending`.

This is especially valuable because your architectural principle is that extensions should compose without making each other's failure modes contagious.

## R3-5 — P2/P3: semantic compaction interception is not fully correlated to the request that caused it

Current hook logic is:

```ts
if (event.reason === "overflow" ||
    requestedCompaction?.reason !== "semantic") {
  return undefined;
}
```

The good part is that overflow is categorically excluded.

The remaining problem is that it does not require the event to be the **manual compaction generated by LCM's semantic request**. Pi's `ctx.compact()` is asynchronous and delegates to Pi's manual `AgentSession.compact()`.

Thus, while `requestedCompaction` is semantic, another compaction event can theoretically be mistaken for it:

```text
semantic request queued/in flight
        ↓
another Pi threshold/manual compaction arrives
        ↓
requestedCompaction.reason === semantic
        ↓
LCM applies deep semantic preparation to that event
```

Similarly, the generic `session_compact` handler clears `requestedCompaction` and `semanticRequested` after an accepted completion, so an unrelated successful compaction can consume the semantic intent.

This is a low-probability race in today's single-root flow, not something I expect constantly. But because R2 deliberately established different semantics for native versus semantic compaction, event correlation now matters more than it did previously.

At minimum:

```ts
if (
  event.reason !== "manual" ||
  requestedCompaction?.reason !== "semantic"
) {
  return undefined;
}
```

Better still, maintain a one-shot state specifically saying the next `manual` `session_before_compact` is the extension request, and only consume semantic intent after that correlated request succeeds.

## R3-6 — P3: root evidence provenance records a reduction before knowing that reduction is safe to keep

In root `tool_result` handling, this happens first:

```ts
if (reduction.category) {
  evidenceTracker.record(reduction.category);
}
```

Then LCM attempts to obtain/save the authoritative full output. If storage fails, it correctly returns the **original, unreduced result**.

That means:

```text
reduction proposed
→ evidenceTracker says "reduced"
→ recovery storage fails
→ original output preserved
→ no reduction actually occurred
```

A later compaction can therefore get an `Evidence completeness:` warning for a reduction that never happened, and reduction diagnostics can disagree with actual transcript behavior. The warning is conservative rather than dangerous, but it weakens telemetry truthfulness.

Move `evidenceTracker.record()` until after a valid recovery path has been established and immediately before returning reduced content. The embedded controller already follows that safer ordering.

## Documentation drift should be cleaned up with the next release

There are now several externally visible contradictions.

The README still says recovery storage has “clean shutdown cleanup,” but PR #19 deliberately removed that cleanup.

More significantly, the configuration guide says a relative `checkpointDirectory` resolves from the **current project**. Current code explicitly resolves it from the **Pi agent directory, never the working tree**—which was one of the audit fixes.

And `keepRecentTokens` is still described as though it generally controls LCM's compaction hook, whereas after R2 it mainly matters for explicitly semantic deep compaction; ordinary proactive and overflow compactions deliberately retain Pi's native preparation.

These aren't runtime failures, but stale docs can cause users to “fix” behavior that is actually already correct.

## Priority before I would call this fully hardened

1. **Fix the above-threshold CompactionGate churn and add the `33k → 33k` regression.**
2. **Make recovery artifacts session-addressable rather than process-global**, with restart reconstruction/TTL semantics.
3. **Cut a new version/tag** so pinned users actually receive the audited code.
4. Make fabric lookup lazy for semantic/reset operations only, and complete cancellation support in `pi-safe-agent-team`.
5. Tighten semantic-compaction event correlation.
6. Move evidence tracking after successful recovery establishment and correct the stale docs.

After those, I think diminishing returns start to become significant. The core architecture is now in much better shape: tool-output reduction is bounded and recoverable, routine proactive compaction delegates the risky summarization mechanics back to Pi, overflow recovery is no longer intercepted, failures back off rather than wedge, and destructive coordination decisions fail closed.

So compared with R2, my assessment has moved materially upward: **the primary local-Qwen failure path is fixed.** R3 is mostly about preventing the new resilience mechanisms themselves from becoming long-run state/lifecycle problems. The one exception is R3-1; I would fix that before relying on current `main` for unattended multi-hour/multi-day local-agent workloads.
