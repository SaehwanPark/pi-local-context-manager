## Round 4 verdict

The Round 3 remediation is substantial and mostly correct. PR #20 and PR #27 genuinely fix the issues they claim to address: the over-threshold gate loop is reduced, routine compaction remains native, semantic interception is narrower, recovery storage is now session-addressable, fabric queries are lazy, evidence accounting is delayed until recoverability is established, and PSAT now propagates cancellation down into broker requests.

I still would **not quite call this final-signoff quality yet**, though the remaining set is much smaller and more focused. I found **two significant correctness issues**, one narrower compaction edge case, and a few release/test-hardening items. There is no new P0.

# R4-1 — P1: PSAT unregisters its interop provider on session replacement and never registers it again

This is the most important joint-project finding.

PSAT registers its fabric provider once, when its extension factory executes:

```ts
registerInteropProvider(
  "safe-agent-team.fabric-state.v1",
  interopProvider,
);
```

But every `session_shutdown` does:

```ts
unregisterInteropProvider(
  "safe-agent-team.fabric-state.v1",
  interopProvider,
);
```

The subsequent `session_start` reattaches the runtime, but **does not re-register the provider**.

That would be fine if `session_shutdown` meant process termination. It does not. Pi documents `session_shutdown` for:

```text
quit
reload
new
resume
fork
```

And `session_start` correspondingly fires for startup/reload/new/resume/fork.  Pi's own lifecycle tests explicitly exercise a `session_shutdown("resume") → session_start("resume")` sequence.

So the actual lifecycle is:

```text
Pi process starts
  ↓
PSAT provider registered
  ↓
session A works normally
  ↓
fork / resume / new session
  ↓
session_shutdown
  ↓
PSAT provider UNREGISTERED
  ↓
session_start
  ↓
PSAT runtime reattaches
  ↓
provider remains absent
```

From this point onward PSAT itself can still operate and spawn children, but LCM no longer sees it.

That is particularly dangerous because LCM intentionally interprets an **absent fabric provider as replacement-safe**:

```ts
if (observation.kind === "absent") {
  return true;
}
```

Therefore, after the first session replacement:

```text
new PSAT children active
       ↓
LCM queries fabric
       ↓
provider absent
       ↓
LCM interprets "PSAT not installed / no fabric"
       ↓
session replacement considered safe
```

That defeats the cross-project protection exactly when users are doing the long-running, multi-session workflows these extensions are intended to support.

### Fix

I would simply make provider registration session-idempotent:

```ts
pi.on("session_start", async (_event, ctx) => {
  registerInteropProvider(
    "safe-agent-team.fabric-state.v1",
    interopProvider,
  );

  ...
});
```

Because the same provider instance is reused, the registry's same-instance behavior already makes this natural.

Alternatively, only unregister on true terminal shutdown, but Pi's extension lifecycle is cleaner if PSAT treats registration as session-scoped and re-establishes it on every `session_start`.

Add a regression that actually runs:

```text
extension factory
→ session_start(A)
→ verify provider
→ session_shutdown(reason="resume")
→ session_start(B)
→ verify provider again
→ create non-quiescent snapshot
→ verify LCM observes it
```

I would fix this before considering the LCM/PSAT contract hardened.

# R4-2 — P1: crash-corrupted recovery metadata can make an old pointer silently point to new output

The new per-session manifest is the right architecture, but its current persistence semantics introduce a more dangerous failure mode than the old dangling pointers.

The relevant sequence in `SessionRecoveryStorage.save()` is essentially:

```text
increment fileSeq
write output-N-tool.txt
update in-memory managedFiles
prune
write manifest.json
touch heartbeat
```

The output filename is derived from the manifest-backed counter:

```ts
const filename = `output-${this.fileSeq}-${safeTool}.txt`;
await writeFile(path, buffer, ...);
```

and `manifest.json` itself is written directly with `writeFile()`.

Consider a crash:

```text
manifest says:
  fileSeq = 10

LCM writes:
  output-11-bash.txt

process dies before new manifest is durable
```

On restart:

```text
manifest still says:
  fileSeq = 10

next bash recovery save:
  fileSeq++ -> 11

writeFile("output-11-bash.txt", NEW CONTENT)
```

The previous file is silently overwritten.

It gets worse if the process dies during the manifest write itself and leaves malformed JSON. `loadManifestSync()` catches the parse error, but `fileSeq` remains at its initial value while the deterministic session directory is retained. The next save may begin again at `output-1-...`.

The consequence is not merely:

> "old full-output path no longer exists"

Instead:

> **an old transcript path can successfully open and return unrelated newer tool output.**

For evidence-sensitive agent work, that is substantially worse than an ENOENT because the model/user may believe the historical evidence is intact.

The same mechanism creates a race when two Pi processes open the same session concurrently: both can load the same `fileSeq`, choose the same next filename, and race their manifests.

### Fix

Do **not make recovery-object identity depend on durable counter synchronization**.

I would use immutable collision-proof names, for example:

```text
output-<uuid>-bash.txt
```

or exclusive creation:

```ts
open(path, "wx")
```

with retry on `EEXIST`.

Then make the manifest atomic too:

```text
manifest.tmp.<uuid>
  ↓ write + close
rename()
  ↓
manifest.json
```

Even with atomic manifest publication, immutable output filenames are still necessary because there will always be a crash window between creating an output and recording it in the manifest.

On startup, it would also be sensible to reconcile:

```text
manifest entries
    ∪
valid output-* files found in session directory
```

rather than assuming the manifest is the sole truth.

Regression tests I'd add:

```text
1. Manifest fileSeq=10, output-11-bash.txt already exists
   → next save must never alter output-11-bash.txt

2. Truncated/invalid manifest + existing recovery files
   → save must never overwrite any existing file

3. Two SessionRecoveryStorage instances for same session
   → concurrent saves produce distinct immutable paths
```

This is the recovery issue I would prioritize highest on the LCM side.

# R4-3 — P1/P2: the gate can still churn if compaction lands immediately *below* the threshold

PR #20 correctly fixed the exact Round 3 example:

```text
threshold = 32k
compaction -> 33k
33k -> 33k      no rearm
33k -> 33.5k    no rearm
33k -> 35.5k    rearm
```

But `crossedThreshold` creates the symmetric edge case just below 32k:

```ts
const crossedThreshold =
  this.postCompactionTokens < compactThresholdTokens &&
  tokens >= compactThresholdTokens;
```

Consider:

```text
threshold = 32,000
rearm     = 24,000

compaction lands at 31,900

next tiny amount of context:
31,900 → 32,000
```

Now `crossedThreshold === true`, despite only 100 tokens of post-compaction growth.

The gate rearms immediately. The two-turn cooldown delays execution, but doesn't require additional meaningful growth. A context dominated by an irreducible large recent turn can therefore cycle roughly like:

```text
32.xk → compact → 31.9k
two turns
32.xk → compact → 31.9k
two turns
...
```

That is narrower than the R3 bug, but it still produces repeated expensive summarization around the boundary on a local model.

The simplest model is actually more consistent:

> Once a successful compaction lands **above the rearm watermark**, require meaningful post-compaction growth before another proactive compaction.

You don't really need `crossedThreshold` for permission. `shouldTriggerThresholdCompaction()` already independently guarantees that requests only happen when the current context is at/above the threshold.

So I would prefer:

```ts
if (!this.armed && this.postCompactionTokens !== null) {
  if (hasMeaningfulGrowth) {
    this.armed = true;
  }
}
```

while preserving the existing immediate rearm when context actually falls to/below `rearmTokens`.

Regression:

```text
complete(31_900)
observe(32_000, 32_000) -> still disarmed
observe(32_500, 32_000) -> still disarmed
observe(34_300, 32_000) -> armed
```

This would make the hysteresis rule much easier to reason about too.

# R4-4 — P2: “active session” recovery lease is still not really a live-session lease

The recovery sweeper now uses a heartbeat, which is an improvement. But the heartbeat is refreshed when recovery storage is written or when a known recovery path is explicitly referenced.

It is **not** a periodic process/session heartbeat.

So this sequence remains possible:

```text
Day 0
  long output reduced and stored

Day 1–4
  same Pi session is actively coding
  but never rereads that particular recovery path
  and creates no new reduced output

heartbeat becomes >3 days old

another Pi process invokes the stale sweeper
  ↓
live session's recovery directory can be deleted
```

That contradicts the source comment that heartbeat handling ensures a live session's copies are never swept.

There's a related lineage problem after a fork: session B's transcript can contain a recovery pointer created under session A. LCM now selects recovery storage by **current session ID** before calling `noteReferences()`.  The physical file from session A may open perfectly, but referencing it from B does not refresh A's LRU/lease because B's storage instance does not own that path.

Two reasonable approaches:

* Treat the 3-day policy explicitly as a TTL, disclose it in the retained-output notice, and accept expiration independent of live Pi activity; or
* Make it a genuine lease by periodically/throttled touching active session storage, and refresh the owner session when a recovery path from an ancestor is accessed.

Given your goal of resumable forensic recovery, I prefer the second.

A once-per-hour touch during a normal session lifecycle would be trivial overhead and would make “live sessions are not swept” actually true.

# R4-5 — P2 hardening: manifest entries should never be trusted as arbitrary filesystem paths

The persisted manifest contains absolute paths. On load, LCM accepts entries when they have a string `path`, numeric `size`, and the target exists. Later pruning executes:

```ts
rm(oldest.path, { force: true })
```

There is no validation that the loaded path is:

```text
inside this session's recovery directory
AND
a valid LCM recovery filename
```

So a corrupted/tampered manifest could add:

```json
{
  "path": "/some/unrelated/file",
  "size": 123
}
```

and eventually cause LCM pruning to delete it.

This is not a remote privilege escalation—the manifest lives under the user's temp state—but durable state parsers should still fail closed.

On load, I would require:

```text
real/normalized parent == sessionDir
basename matches expected recovery naming
size is safe non-negative integer
optional stat size reconciliation
manifest.sessionId == this.sessionId
```

This becomes especially natural if output files move to immutable UUID names.

# R4-7 — CI still does not exercise the most important joint lifecycle

This is increasingly worth fixing because it would have caught R4-1.

LCM's PR #20 CI is green across Linux, macOS, and Windows, with the expanded unit suite. But its real-Pi smoke still skipped three companion-extension cases in the Ubuntu run.

PSAT already provides useful scripts:

```text
smoke:pi
smoke:pi:with-lcm
smoke:pi:integration
```

Yet the PSAT CI workflow runs only:

```text
npm run check
npm run build
```

I would add a small joint contract CI job, probably Ubuntu-only to avoid tripling cost:

```text
checkout PSAT
checkout compatible LCM sibling
install both
run model-free joint smoke

then a deterministic lifecycle test:
session A start
→ provider visible
→ resume/fork lifecycle
→ session B start
→ provider still visible
```

The model-backed smoke can remain optional/nightly because it requires credentials. The lifecycle and interop-registry contract needs no model and should be mandatory.

## PSAT PR #27 itself looks good

I specifically tried to find a second-order problem in the cancellation implementation. The basic implementation is sound:

* pre-aborted signals reject;
* abort after connection is checked;
* pending-map entries are removed;
* timer and abort listeners are cleaned;
* idempotent calls do not retry an explicitly aborted request;
* `getFabricStateSnapshot()` passes the signal to `status()`.

That closes the actual R3 cancellation concern.

An aborted broker request cannot retract a frame that has already reached the broker, of course, but `fabric.status` is read-only, so that's entirely acceptable for this use case.

## What I would fix before declaring the audit cycle complete

My ordering would now be:

1. **PSAT: re-register the fabric provider on every `session_start`.**
2. **LCM: make recovery output identities immutable/collision-proof and manifest publication crash-safe.**
3. **LCM: remove the tiny-growth `crossedThreshold` rearm path.**
4. Harden recovery manifests to reject paths outside their session directory.
5. Decide whether recovery is truly lease-based or TTL-based; implement/document consistently.
6. Add one mandatory joint lifecycle CI test.
7. Create the actual `v0.5.0` tag after those corrections.

After those, I would be comfortable moving from repeated adversarial remediation into **maintenance-mode auditing** rather than continuing R5/R6 indefinitely. The issues are no longer pointing to a flawed overall architecture. They are now mostly consequences of making the architecture more durable and compositional.

The major conceptual goals are now in the right place: **Pi owns emergency compaction, LCM controls conservative proactive policy, semantic compaction is exceptional, recovery evidence is durable rather than disposable, PSAT coordination fails closed when visible, and optional cross-extension communication is cancellable.** The remaining two P1s are quite localized and should be straightforward to close.
